# Handoff — `AttachmentClass::GetType()` on a string, `snapshot-20260929-134629`

Prepared 2026-10-02 from the Player Count chat. Everything here was read out of
the snapshot and the binaries; nothing is inferred from source alone.

## Verdict

`TAExt_RunInstantSpawns` calls `AttachmentClass::GetType()` on an
`AttachmentClass*` whose value is the **ASCII bytes `"date"`**. A string is
being used as an object pointer. The null check in front of the call passes
because `0x65746164` is not zero.

**Confidence: high.** The faulting instruction, the register, the caller and the
guard that let it through are all identified. What is *not* yet identified is
where the `"date"` bytes come from — see "The one open question".

## The faulting site, from the matched binary

`TAExt_RunInstantSpawns` at `+0x11A`:

```asm
10007fab  mov  eax,[ebp-0x20]     ; the container/host being walked
10007fae  mov  ecx,[eax+0x0c]     ; ecx = <that>->+0x0C  == the AttachmentClass*
10007fb1  test ecx,ecx
10007fb3  je   0x1000800a         ; <-- guard. PASSES: "date" != 0
10007fb5  call 0x100133b0         ; AttachmentClass::GetType(), ECX = this
10007fba  test eax,eax            ; <-- the return address seen on the stack
10007fbc  je   0x1000800a
10007fbe  mov  edi,[eax+0xc8]     ; AttachmentTypeClass vector end
10007fc4  mov  esi,[eax+0xc4]     ;   ...and begin
10007fca  cmp  esi,edi
10007fcc  je   0x1000800a         ; empty -> skip
```

`GetType()` is a 13-byte leaf (`0x100133B0..0x100133BC`); `+0x9` is its single
load off `this`. With `this = 0x65746164` that load faults immediately.

So the bad pointer is **the value at `[<object at ebp-0x20>] + 0x0C`**, and the
only protection on it is a non-null test.

## The one open question

Where do the bytes `"date"` come from?

**A field read at the wrong offset.** If the object at `[ebp-0x20]` is not the
type `RunInstantSpawns` believes it is, `+0x0C` may land inside an inline
`char[]` — e.g. `AbstractTypeClass::ID` is an inline `char ID[0x18]` at `+0x24`,
*not* a pointer, so any off-by-one in a struct walk over types yields exactly
this: four characters of a name sitting in a pointer slot.

**Ruled out: the varargs/`PhobosFixedString` bug.** My first instinct was the
class-passed-to-`%s` trap, since that produces string bytes where a pointer is
expected. It does not apply here — I checked:

- the fix landed in `7e7a3e7` (2026-09-15), **ten days before** the deployed
  build, so the crash-run DLL already had it;
- `tools/check_log_varargs.py` passes clean over all 43 files.

Useful corollary for whoever picks this up: `src/New/Entity/AttachmentClass.cpp`
has **no commits since 2026-09-25**, and the deployed DLL is commit `4a3b88b`
(2026-09-25 02:15). So for this file the current tree *is* the crashing code —
read it directly and trust it.

**How to settle it in one step:** read the object at `[EBP-0x20]` out of the
dump. EBP is `0x00C9CF18`, so the slot is `0x00C9CEF8`. Dereference it, dump
0x40 bytes, and look at what `+0x0C` is a member of — and whether `"date"` is
part of a longer string a few bytes earlier (grep the surrounding 0x80 bytes for
printable runs). If it reads as `...date` mid-identifier, it is shape 1.

Tooling is in `tools/` (copied in alongside this file):

```
python3 tools/minidump.py        # MD class: streams 3/4/6/9, Memory64List reader
python3 tools/dump_patches.py --dmp <dmp> --exe gamemd-spawn.exe --range 0xA-0xB
```

## Hook geometry — ruled out

`TechnoClass_ReceiveDamage_InstantSpawn_TAExt` is the entry point for this path.
This is **not** a stolen-bytes/resume-boundary defect: the fault is a data
dereference inside a handler that was entered normally, with a correct return
address on the stack. No `E9` patch is involved at the faulting address (it is
inside our own DLL image, not the exe).

## Suggested fix shape

Independent of which shape above is true, the guard at `0x10007FB1` is the wrong
kind of check. A non-null test cannot validate a pointer that was never a
pointer. Two options, in order of preference:

1. **Fix the read.** Once the dump identifies the container, correct the offset
   or the type. This is the real fix.
2. **Validate by membership, not by dereference.** If `RunInstantSpawns` walks
   attachments reachable from a Techno, assert the candidate is in that
   Techno's own attachment list before calling `GetType()` — the pattern
   BuildQueueExt used for `FactoryClass` (`for (auto p : FactoryClass::Array)`)
   after the same class of crash.

The varargs lint already exists (`tools/check_log_varargs.py`) and is green, so
there is nothing to add on that front.
