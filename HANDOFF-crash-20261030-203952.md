# Handoff — `AttachmentClass::Unlimbo` uses a null `Parent`, `snapshot-20261030-203952`

Prepared 2026-10-30 from the Player Count chat. Diagnosis is complete: the
faulting instruction, the null field, the live object state and the mechanism
that nulls it are all read out of the dump and the matched binary. Nothing here
is inferred from source alone.

## Verdict

`AttachmentClass::Unlimbo()` guards **only `Child`**, then uses `Parent` three
times. An attachment was sitting in a techno's `ChildAttachments` with
`Parent == nullptr`, so the first use — passing it to
`TechnoExt::GetFLHAbsoluteCoords`, which dereferences its argument on line one —
read address 0.

Proven from the dump, not deduced:

```
AttachmentClass @0x18DAF058
   +00 Data   = 0x17034248   valid (FLH 0,0,40, IsOnTurret=1)
   +04 Parent = 0x00000000   <<< NULL
   +08 Child  = 0x152696B8   live UnitClass, type 'USAGUN'
```

## The exception

```
ExceptionCode    0xC0000005
ExceptionAddress 0x775FFD3E        (== except.txt EIP)
param[0] = 0  (READ)   param[1] = 0x00000000
```

`0x775FFD3E` = `TechnoAttachmentExt.dll+0x1FD3E` =
**`TechnoExt::GetFLHAbsoluteCoords + 0xE`**.

```asm

1001fd3b  mov  ecx,esi
1001fd3e  mov  eax,[esi]         ; *** FAULT: ESI = 0, read at 0x00000000
1001fd40  call [eax+0x84]        ; GetTechnoType()
```

`ESI = ECX = 0` in the register dump, and the callee's very first line is
unguarded ([`src/Ext/Techno/Body.cpp:115`](src/Ext/Techno/Body.cpp)):

```cpp
CoordStruct TechnoExt::GetFLHAbsoluteCoords(TechnoClass* pThis, CoordStruct pCoord, bool isOnTurret)
{
    auto const pType = pThis->GetTechnoType();      // no null check
```

### Method note

My first parse of the exception record reported "`param[0] = 2` (WRITE) at
`0x00000000`", which contradicted a `mov eax,[esi]`. That was my bug:
`MINIDUMP_EXCEPTION`'s `ExceptionRecord` and `ExceptionAddress` are **ULONG64**,
and `ExceptionInformation[]` starts at **+0x28** within the stream (not +0x20).
Reading them as 32-bit made `NumberParameters` look like `param[0]`. Correct
offsets: `+0x08` Code, `+0x18` Address (u64), `+0x20` NumberParameters,
`+0x28`/`+0x30` Info[0]/Info[1] (u64 each).

## Resolved chain

```
TechnoClass_Unlimbo_UnlimboAttachments  +0xE     (TAExt+0x397E)   hook @0x6F6F20
  TechnoExt::UnlimboAttachments         +0x27    (TAExt+0x221F7)
    AttachmentClass::Unlimbo            +0x3A    (TAExt+0x14A2A)
      TechnoExt::GetFLHAbsoluteCoords   +0xE     (TAExt+0x1FD3E)  *** FAULT
```

`EDI` at the fault is still `Unlimbo`'s `this` (`GetFLHAbsoluteCoords` pushes
`edi` only *after* the faulting instruction), which is how the attachment object
above was recovered.

## The compiled code names the fields for you

```asm
100149f8  mov  edi,ecx            ; this
100149fa  cmp  [edi+0x8],0        ; this->Child
```

Member layout confirmed against the header: `+0x00 Data`, `+0x04 Parent`,
`+0x08 Child`, `+0x0C RespawnTimer`, `+0x18 LastPrereqLost`.

**Guarding the callee is not sufficient** — line 1629 dereferences `Parent`
twice more, immediately. The guard belongs at line 1623.

## How `Parent` becomes null while the slot stays in the vector

[`AttachmentClass.cpp:1744`](src/New/Entity/AttachmentClass.cpp):

```cpp
void AttachmentClass::InvalidatePointer(void* ptr)
{
    AnnounceInvalidPointer(this->Parent, ptr);   // nulls Parent
    AnnounceInvalidPointer(this->Child, ptr);
}
```

That nulls `Parent` in place and **removes nothing from any
`ChildAttachments` vector**. Meanwhile
[`Body.TechnoAttachment.cpp:155`](src/Ext/Techno/Body.TechnoAttachment.cpp)
walks that vector unconditionally:

```cpp
void TechnoExt::UnlimboAttachments(TechnoClass* pThis)
{
    auto const pExt = TechnoExt::ExtMap.Find(pThis);
    if (!pExt)                        // <- the 13a14b1 fix, working as intended
        return;

    for (auto const& pAttachment : pExt->ChildAttachments)
        pAttachment->Unlimbo();       // no null check on pAttachment either
}
```

So the invariant "a slot in `ChildAttachments` has a live `Parent`" is not
maintained. Note this is the **mirror image** of the bug `a109be7` fixed: that
one was a live `ParentAttachment` pointer naming a destroyed slot; this one is a
live slot whose `Parent` has been cleared. `LiveSet` / `GetLiveParentAttachment()`
protect the former and do nothing for the latter — `Parent` is a `TechnoClass*`,
not an `AttachmentClass*`.

## Fix

1. **The gate** — [`AttachmentClass.cpp:1623`](src/New/Entity/AttachmentClass.cpp):

   ```cpp
   if (this->Child && this->Parent)
   ```

   This alone stops the crash.

2. **`UnlimboAttachments`** — add the null check the sibling
   `DestroyAttachments` already has (`if (!pAttachment) continue;`).

3. **`GetFLHAbsoluteCoords`** — it is a public static taking a raw
   `TechnoClass*` and dereferencing it unguarded on line one. A null check
   returning `CoordStruct{}` makes every present and future caller safe.

### Fix-the-class: 31 sites

`grep -c 'this->Parent->' src/New/Entity/AttachmentClass.cpp` → **31**, and only
a few are guarded (642 and 1382 are; most are not). Two deserve attention now
because they are the same shape as the crash:

- **`AttachmentClass::GetChildAnchor()`** (line ~352) passes `this->Parent`
  straight into `GetFLHAbsoluteCoords` — a second instance of the exact faulting
  call, unguarded.
- **line 1490** is the same `IsOnTurret ? Parent->SecondaryFacing :
  Parent->PrimaryFacing` pair as 1629, also unguarded.

Fixing `GetFLHAbsoluteCoords` itself (item 3) covers the first for free; the
facing reads need a guard at their own gate.

A checker in the style of the repo's existing `tools/check_log_varargs.py` /
`check_member_init.py` — flag `this->Parent->` where no `this->Parent` null test
dominates it in the same block — would close the category rather than this
instance.

## Observed but NOT the cause

The attachment's `RespawnTimer` region carries heap debug fill:

```
   +0x0C = 0xFFFFFFFF
   +0x10 = 0xBAADF00D     <- "uninitialised heap allocation" pattern
   +0x18 = 0x00000001     LastPrereqLost == 1 ("prerequisite unmet")
   +0x1C = 0xABABABAB     <- heap no-man's-land, i.e. past the object
```

Both constructors do initialise `RespawnTimer { }`, so `0xBAADF00D` inside it is
odd — but `CDTimerClass` is a game struct whose default construction may not
write every word, and `0xABABABAB` at `+0x1C` is simply the allocator's guard
beyond a `0x1C`-byte object. **I am not claiming the object was unconstructed.**
It is recorded here only so nobody re-derives it and mistakes it for the cause;
`Data` and `Child` are both valid, which an unconstructed object would not have.

`LastPrereqLost == 1` means the slot's dynamic prerequisite was last seen
**unmet** — worth a glance when reproducing, since the prerequisite-hide path
(line 1421, `this->Parent->InLimbo`, also unguarded) is adjacent to this state.
