# Handoff — a TerrainClass reaches `DestroyAttachments`, `snapshot-20261019-224522`

Prepared 2026-10-23 from the Player Count chat. Everything here was read out of
the minidump and the matched binaries. Frame reconstruction is anchored and
self-verifying (see "Why the frames are trustworthy") — unlike the two earlier
handoffs, nothing here rests on an unanchored stack word.

## Verdict

`TechnoClass::KillCargo` recursed into a **`TerrainClass`** (a tree) that was
sitting in a **building's** passenger list. TAExt's hook at `0x707CB3` reads
`EBX` as a `TechnoClass*` with a blind `GET`, so the tree was passed to
`TechnoExt::DestroyAttachments`, which looked it up in `TechnoExt::ExtMap`
(trees are never registered there), got `nullptr`, added the
`ChildAttachments` offset and dereferenced it.

```
EAX = 0x00000010   =   nullptr + 0x10
```

**Two defects are ours and both are one-liners.** A third — why a tree is in a
building's cargo at all — is upstream of us and *not* TAExt's to fix.

## Why the frames are trustworthy

The Syringe stub's `pushad` block is a self-checking anchor. With the origin
slot found at `0x00C9CC90`:

```
origin      @0x00C9CC90 = 0x00707CB3   == the hooked address        ✓
pushed esp  @0x00C9CC8C = 0x00C9CC90   == the origin slot itself    ✓
EDI         @0x00C9CC98 = 0x1EDE546C
EBX         @0x00C9CCA8 = 0x1B064A60   <- pThis AS READ BY THE HOOK
ECX         @0x00C9CCB0 = 0x1B064A60   == EBX, so `this` was valid
saved EBX   @0x00C9CCB8 = 0x1EDE5358   <- the OUTER KillCargo's `this`
ret addr    @0x00C9CCBC = 0x00707CFA   <- the recursive call at 0x707CF5
```

And the clincher: `EDI − outer EBX = 0x1EDE546C − 0x1EDE5358 = 0x114`, exactly
the `CargoClass` member offset that `0x707CC4: lea edi,[ebx+0x114]` computes.
Three independent values agree, so this is the live chain, not residue.

## The objects, identified rigorously

`WhatAmI()` is vtable slot `+0x2C` and `Size()` is `+0x30` — **both** are
`mov eax,imm32; ret`, so a naive "first constant-returning thunk" scan returns
`Size()` and silently lies. Read by slot, cross-checked against a known object:

| Object | vtable | `WhatAmI` (+0x2C) | `Size` (+0x30) |
|---|---|---|---|
| control: the `SREF` in `EBP` | `0x007F5C70` | **1 = Unit** ✓ | 2280 |
| outer transport `0x1EDE5358` | `0x007E3EBC` | **6 = Building** | 1824 |
| `pThis` `0x1B064A60` | `0x007F522C` | **36 = Terrain** | **224** |

A 224-byte object cannot be any `TechnoClass` (a `UnitClass` is 2280), so the
AbsID and the size agree independently: **`pThis` is a `TerrainClass`.**

The transport's cargo head now reads `[+0x114]=4, [+0x118]=0` — the list was
emptied, consistent with `RemoveFirstPassenger` having just detached the tree.

## The engine path

```asm
707cb0  push ebx
707cb1  mov  ebx,ecx            ; ebx = this  (so reading EBX at 0x707CB3 IS correct)
707cb3  mov  eax,[ebx+0x118]    ; <-- our hook steals these 6 bytes
707cbb  je   0x707d1c           ; no cargo -> out
707cc4  lea  edi,[ebx+0x114]    ; &this->Passengers (CargoClass)
707ce7  call 0x473430           ; CargoClass::RemoveFirstPassenger
707cec  mov  esi,eax            ; esi = the detached passenger
707cf0  je   0x707d0f           ; null -> out
707cf5  call 0x707cb0           ; *** RECURSE: KillCargo(passenger)
```

So `BuildingClass::Destroy` → `KillCargo(building)` → `RemoveFirstPassenger`
returned the tree → `KillCargo(tree)` → our hook → crash.

`0x707CB3` has **exactly one handler** (ours) — verified with
`tools/dump_patches.py`. No chain clobbered anything.

One live byte in this function looks alarming and is **not** a bug:
`0x707CF2 disk=56 (push esi) → live=55 (push ebp)`, with no stub. It is
Phobos's deliberate `DEFINE_PATCH(0x707CF2, 0x55)` from
`Misc/Hooks.BugFixes.cpp` — *"Fixes recursive passenger kills not being
accredited to proper techno but to their transports"*. Don't chase it.

## Fix

Two guards, both ours:

1. **`Hooks.Attachment.cpp:171`** — stop blind-casting. The engine's `KillCargo`
   recursion can hand this seat **any `ObjectClass`** that ended up in a cargo
   list, not just technos. Use a type-checked cast:

   ```cpp
   GET(ObjectClass*, pObj, EBX);
   auto const pThis = abstract_cast<TechnoClass*>(pObj);
   if (!pThis)
       return 0;
   ```

2. **`Body.TechnoAttachment.cpp:68`** — the ext lookup is nullable **by design**:

   ```cpp
   extension_type_ptr TryFind(key) const { if (!key) return nullptr; ... }  // checks key
   extension_type_ptr Find(key)    const { ... MappedItems.find(key); }     // does NOT
   ```

   `Find()` returns null whenever the key isn't in the map. Guard it:

   ```cpp
   auto const pExt = TechnoExt::ExtMap.Find(pThis);
   if (!pExt)
       return;
   ```

Either one alone stops this crash; both are correct.

### Fix-the-class, worth a sweep

There are **72** `TechnoExt::ExtMap.Find(` sites in `src/`. Several share the
assign-then-immediately-dereference shape, e.g.
`Hooks.AttachedFactory.cpp:38`, `Hooks.AttachedSelection.cpp:98/152/167/209`,
`Hooks.InstantSpawn.cpp:221`. This repo already has `tools/check_log_varargs.py`
and `tools/check_member_init.py`; a third checker in the same style — flag a
`Find(` result dereferenced with no intervening null test — would close the
category rather than this instance.

Also worth auditing: every `GET(TechnoClass*, …)` on a seat the engine can
reach with a non-techno `ObjectClass`.

## NOT ours, and genuinely open

**Why is a `TerrainClass` in a building's passenger list?** Nothing in the above
explains that, and it is upstream of TAExt — our guards turn the crash into a
no-op but do not address it. Unproven leads, in the order I would check:

- **PayloadExt** — the garrison/occupancy DLL; it synthesises `Occupier` and
  manipulates building occupants directly.
- **MirageTreesExt** — the one component whose whole job is units and trees.
- **Phobos** — hooks `CargoClass::Attach` at `0x4733BD`
  (`CargoClass_Attach_HandleCurrentAttachMode`).

The dump can settle it: the tree object is still intact at `0x1B064A60` and the
building at `0x1EDE5358`. Walking back-references to the tree, or checking
whether its `TerrainTypeClass` corresponds to a mirage disguise, should name the
owner.

## A correction worth recording

My first pass on this crash reported **"`pThis` was NULL"**. That was wrong.
I read the first argument slot at `[ebp+0x8]` and found 0 — but
`0x10020FC4: mov [ebp+0x8],ebx` **reuses that slot** to hold
`pThis->CurrentMission`, and the mission was 0 (`Mission::Sleep`). The real
`pThis` is in the stub's `pushad` block and is non-null. The lesson: on an
optimised build, read arguments from the stub's register snapshot, not from
argument slots the callee may have recycled.
