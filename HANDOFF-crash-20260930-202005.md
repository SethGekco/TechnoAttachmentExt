# Handoff — locomotor virtual call into freed memory, `snapshot-20260930-202005`

Prepared 2026-10-02 from the Player Count chat. Everything here was read out of
the snapshot and the binaries.

## Verdict

`AttachmentLocomotionClass::In_Which_Layer()` delegates to the parent's
locomotor via a COM vtable call. The parent's locomotor has been **freed and its
memory recycled into an `std::unordered_map` bucket array**, so the "vtable
pointer" read out of it is a bucket pointer, and the call jumps into container
storage and executes pointer bytes as code.

**Every null guard on the path passed**, because freed-but-reallocated memory is
not null. That is the whole bug: liveness cannot be tested by dereferencing.

**Confidence: high** on the mechanism and the faulting instruction. **Open:**
which object's lifetime ended (locomotor vs. `Parent`), and why `InvalidatePointer`
did not cover it — see "Why the existing invalidation didn't save it".

## The faulting site, from the matched binary

`In_Which_Layer` ends at `0x100238BE`; `+0x99` is `0x100238B9`, the instruction
*after* the indirect call:

```asm
10023892  mov   ecx,[esi+0x4]          ; GetAttachment()  -> pAttachment
10023895  test  ecx,ecx
10023897  je    0x100238c1             ; guard 1  -> CalculateLayer()
10023899  test  BYTE [ecx+0x14],0x4    ; ResolveInheritHeightStatus(), inlined
1002389d  mov   eax,0x0
100238a2  cmovne eax,ecx
100238a5  test  eax,eax
100238a7  je    0x100238c1             ; guard 2  -> CalculateLayer()
100238a9  mov   ecx,[eax+0x674]        ; the parent's Locomotor
100238af  test  ecx,ecx
100238b1  je    0x100238c1             ; guard 3  -> CalculateLayer()
100238b3  mov   eax,[ecx]              ; eax = <locomotor>->vtable   *** POISON
100238b5  push  ecx
100238b6  call  DWORD PTR [eax+0x74]   ; ILocomotion::In_Which_Layer()  *** FAULT
100238b9  pop   edi                    ; <-- the return address on the stack
```

Which maps exactly onto
[`src/Locomotion/AttachmentLocomotionClass.cpp:172`](src/Locomotion/AttachmentLocomotionClass.cpp):

```cpp
Layer AttachmentLocomotionClass::In_Which_Layer()
{
    AttachmentClass* pAttachment = this->GetAttachment();
    if (!pAttachment || !pAttachment->ResolveInheritHeightStatus())
        return this->CalculateLayer();

    auto const pParentAsFoot = abstract_cast<FootClass*>(pAttachment->Parent);
    return pParentAsFoot && pParentAsFoot->Locomotor
        ? pParentAsFoot->Locomotor->In_Which_Layer()   // <-- here
        : this->CalculateLayer();
}
```

`[eax+0x74]` is slot 0x1D of the `ILocomotion` COM vtable. `eax` came from
`[ecx]` where `ecx` is the locomotor — and `[ecx]` held a bucket pointer, so
`[bucket+0x74]` was another bucket pointer, and the call landed inside the
bucket array. Consistent in every detail with EIP's surroundings.

## Why the existing invalidation didn't save it

The repo **already** hooks `AnnounceInvalidPointer`:

```
src/Hooks.Attachment.cpp:32   DEFINE_HOOK(0x7258D0, TechnoAttachmentExt_AnnounceInvalidPointer, 0x6)
src/Ext/Techno/Body.cpp:23    TechnoExt::ExtData::InvalidatePointer(void*, bool)
src/New/Entity/AttachmentClass.h:189   void InvalidatePointer(void* ptr);
```

So "add an invalidation hook" is **not** the fix — it exists. Something slips
past it. Three candidates, in order of likelihood:

1. **The locomotor is not a pointer the engine announces.** `0x7258D0` broadcasts
   `AbstractClass*` invalidation. An `ILocomotion` COM object is reference-counted
   and freed on its *own* schedule — when a `FootClass`'s locomotor is replaced
   or released, no `AnnounceInvalidPointer` fires for it. Scrubbing `Parent`
   therefore does nothing to protect `Parent->Locomotor`.
   **This is the leading theory** and it is consistent with guard 3 passing:
   `Parent` was valid, `Parent->Locomotor` was non-null, and the pointed-to COM
   object was dead.
2. **`Parent` was freed and `ResolveInheritHeightStatus()` read garbage.** Guard 2
   is a *flag test* (`test BYTE [ecx+0x14],0x4`), which a freed block passes
   ~50% of the time by luck.
3. **Ordering:** the announce fires, but `In_Which_Layer` is called from the
   engine's draw/layer pass *within* the same teardown before scrubbing lands.
   The Antares chain above `gamemd+0xDB803` is a real call path worth
   identifying — it may be a removal/limbo path.

**Ruled out as a lead:** Magnetron locomotor swapping. The published trap is that
a Magnetron grab *destroys* the victim's old locomotor rather than saving it
(see the `yr-magnetron-is-jumpjet-loco` note), which would be a perfect fit —
but I grepped this run's 154 MB log for `magnetron|magneto|MAGBEAM` and got
**zero hits**. Not this.

## How to settle it

The dump has full memory. From `ESI` (`0x1AC4B468`) walk
`ESI+0x4 -> pAttachment`, then `+0x674 -> locomotor`, and inspect each:

- Does `pAttachment` still look like an `AttachmentClass` (sane `Parent`,
  `Child`, type pointer), or is it recycled heap?
- Is `Parent` in `TechnoClass::Array`? **Note:** `Count` is at **`+0x10`**, not
  `+0x0C` — `+0x0C` is the `IsInitialized`/`IsAllocated` bool pair and reads as
  `0x00000101` = 257 for every array. (Cost me a wrong conclusion once already.)
  `UnitClass::Array` = `0x8B4108`, `InfantryClass::Array` = `0xA83DE8`.
- Is the locomotor block still a COM object, or is it inside the bucket array?
  If `[locomotor]` points into `0x18655Exx`, the locomotor itself is the freed
  thing → theory 1, and the fix is locomotor-lifetime, not pointer-scrubbing.

## Suggested fix shape

If theory 1 holds, the robust fix is to stop reaching through `Parent->Locomotor`
at all from the locomotion overrides. The file already has the right helper —
`GetAttachmentParentLoco()` returns an `ILocomotionPtr`, i.e. a **ref-counted
smart pointer** that keeps the object alive for the duration of the call.
`Is_Moving_Now()`, `Apparent_Speed()` and friends use it; `In_Which_Layer()` and
`Draw_Matrix()` reach for the raw `pParentAsFoot->Locomotor` instead. Making
`In_Which_Layer()` use `GetAttachmentParentLoco()` would both fix this crash and
make the file internally consistent.

Note `Draw_Matrix()` at line 31-33 has the same raw-pointer shape **and no null
check at all** (`pParentFoot->Locomotor->Draw_Matrix(key)`), so it is strictly
more exposed than the site that actually crashed. Worth fixing in the same pass.
